# PriceWatch — Month 1 Product Requirements Document (PRD)

**Version:** 1.0  
**Phase:** Month 1 — Foundation  
**Target effort:** 3–5 hours/week  
**Status:** Sample / Learning Project

## 1. Product Overview

PriceWatch is a backend service that lets users keep track of products and record their prices over time.

The long-term product will periodically check product prices and notify users when a price reaches a target value. Month 1 deliberately implements only the foundational synchronous backend: users, products, price watches, and price history.

### Month 1 goal

By the end of Month 1, a user should be able to:

1. Create an account.
2. Create a product.
3. Create a price watch for that product.
4. View their watches.
5. Record and view price history.
6. Retrieve product details.

The system does **not** automatically check external stores yet.

## 3. Primary User and Example

The primary user wants to monitor product prices.

Example:

A user adds:

- Product: `Example Laptop 15`
- URL: `https://store.example/products/laptop-15`
- Current price: `1200.00`
- Currency: `EUR`

They then create a watch:

- Target price: `1000.00`
- Active: `true`

Future price observations are stored in `PriceHistory`.

# 4. Functional Requirements

## FR-01 — Create User

**Endpoint:** `POST /api/v1/user/[register|login|update-password]`

### Request
register:
```json
{
  "username": "user@example.com",
  "password": "secret-password",
  "password-confirm": "secret-password"
}
```
login:
```json
{
  "username": "user@example.com",
  "password": "secret-password"
}
```
update-password:
```json
{
  "oldPassword": "secret-password",
  "newPassword": "new-secret-password"
}
```

### Requirements

- Email is required and must be valid.
- Email must be unique.
- Password is required and must meet a minimum length.
- Password must never be stored as plain text.
- The API returns the jwt token containing username

### Example response
Login/Register
```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJzb2JoYW4uYXJ5YW5uYW1hemlAZ21haWwuY29tIiwiaWF0IjoxNzg5NjQzNzMwLCJleHAiOjE3ODk3MzAxMzB9.Qs6YiarhQA2phzui3xPam13EWWL0fxtKVBzafh9LMP4"
}
```
update-passwrod: http response 200

### Acceptance criteria

- Valid input creates a user.
- Existing email produces a suitable client error.
- Invalid email is rejected.
- Missing/invalid password is rejected.
- No password-related field appears in the response.

## FR-02 — Create Product

**Endpoint:** `POST /api/v1/products`

### Request

```json
{
  "name": "Example Laptop 15",
  "url": "https://store.example/products/laptop-15",
  "currentPrice": 1200.00,
  "currency": "EUR"
}
```

### Requirements

- Name is required.
- URL is required and must be valid.
- Price must be >= 0.
- Currency is required and should use a three-letter code such as EUR/USD/GBP.
- ID and timestamps are generated by the server.

### Acceptance criteria

- Valid products are persisted.
- Invalid URLs are rejected.
- Negative prices are rejected.
- Missing required fields are rejected.

---

## FR-03 — Get Product

**Endpoint:** `GET /api/v1/products/{productId}`

Return product details.

Existing product → HTTP 200.  
Unknown product → HTTP 404.

Example:

```json
{
  "id": 42,
  "name": "Example Laptop 15",
  "url": "https://store.example/products/laptop-15",
  "currentPrice": 1200.00,
  "currency": "EUR",
  "createdAt": "2026-09-10T12:00:00Z",
  "updatedAt": "2026-09-10T12:00:00Z"
}
```

---

## FR-04 — Update Product

**Endpoint:** `PUT /api/v1/products/{productId}`

Allow updating:

- Name
- URL
- Current price
- Currency

Update `updatedAt`.

---

## FR-05 — Create Price Watch

**Endpoint:** `POST /api/v1/watches`

### Request

```json
{
  "userId": 1,
  "productId": 42,
  "targetPrice": 1000.00
}
```

### Requirements

- User must exist.
- Product must exist.
- Target price must be >= 0.
- New watches are active by default.
- A user should not have duplicate active watches for the same product.

### Acceptance criteria

- Valid watch is created.
- Unknown user/product is rejected.
- Invalid target price is rejected.
- Duplicate active watch is rejected.

**Temporary Month 1 note:** `userId` may be supplied directly because authentication is a Month 2 feature. Remove this from the public contract when JWT authorization is introduced.

---

## FR-06 — List User Watches

**Endpoint:** `GET /api/v1/users/{userId}/watches`

Return the watches belonging to the specified user.

Example:

```json
[
  {
    "id": 100,
    "productId": 42,
    "productName": "Example Laptop 15",
    "targetPrice": 1000.00,
    "currentPrice": 1200.00,
    "currency": "EUR",
    "active": true
  }
]
```

---

## FR-07 — Delete Price Watch

**Endpoint:** `DELETE /api/v1/watches/{watchId}`

Successful deletion → HTTP 204.  
Unknown watch → HTTP 404.

---

## FR-08 — Record Price Observation

For Month 1, price observations may be created manually through an API endpoint.

**Endpoint:** `POST /api/v1/products/{productId}/price-history`

### Request

```json
{
  "price": 1150.00,
  "currency": "EUR"
}
```

Requirements:

- Product must exist.
- Price must be >= 0.
- Timestamp is generated by the server.
- Observation is immutable.

---

## FR-09 — Get Price History

**Endpoint:** `GET /api/v1/products/{productId}/price-history`

Return observations newest first.

Example:

```json
[
  {
    "price": 1150.00,
    "currency": "EUR",
    "recordedAt": "2026-09-10T13:00:00Z"
  },
  {
    "price": 1200.00,
    "currency": "EUR",
    "recordedAt": "2026-09-09T13:00:00Z"
  }
]
```

Simple retrieval is sufficient for Month 1; pagination can come later.

# 7. Technical Requirements

## Technology stack

- Java 21
- Spring Boot
- Spring Web / Spring MVC
- Spring Data JPA
- Hibernate
- PostgreSQL
- Flyway
- Gradle
- JUnit 5
- Mockito

The recommended implementation uses Java for this backend project to strengthen Java/Spring marketability. Kotlin can be added later.

## Architecture

Start as a **modular monolith**:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
PostgreSQL
```

Use DTOs at the API boundary instead of exposing JPA entities directly.

Suggested package structure:

```text
com.pricewatch
├── user
│   ├── User
│   ├── UserController
│   ├── UserService
│   ├── UserRepository
│   └── dto
├── product
│   ├── Product
│   ├── ProductController
│   ├── ProductService
│   ├── ProductRepository
│   └── dto
├── watch
│   ├── PriceWatch
│   ├── PriceWatchController
│   ├── PriceWatchService
│   ├── PriceWatchRepository
│   └── dto
└── pricehistory
    ├── PriceHistory
    ├── PriceHistoryController
    ├── PriceHistoryService
    ├── PriceHistoryRepository
    └── dto
```

The exact structure may evolve; separation of HTTP, business logic and persistence is the important part.

# 8. Error Handling

Use a consistent error format.

```json
{
  "status": 400,
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "timestamp": "2026-09-10T13:00:00Z",
  "errors": [
    {
      "field": "currentPrice",
      "message": "must be greater than or equal to 0"
    }
  ]
}
```

At minimum support:

- `400` — invalid request
- `404` — resource not found
- `409` — resource conflict
- `500` — unexpected server error

Never expose stack traces or database exception details to clients.

---

# 9. Database Requirements

Use Flyway from the beginning.

Suggested migrations:

```text
V1__create_users.sql
V2__create_products.sql
V3__create_price_watches.sql
V4__create_price_history.sql
```

Requirements:

- All schema changes are represented by migrations.
- Foreign keys are explicit.
- Email has a unique constraint.
- Appropriate indexes exist for common lookups.
- Monetary values do not use floating-point database types.

Recommended price representation:

```text
DECIMAL(19, 4)
```

# 14. Questions to Investigate While Building

Don't implement these mechanically. Research them as they arise:

1. Why should API DTOs be separate from JPA entities?
2. What does `@Transactional` actually do?
3. What is the persistence context?
4. What is the difference between `save()` and a database commit?
5. What causes the N+1 query problem?
6. When should a relationship be lazy?
7. Why use `DECIMAL` instead of floating point for prices?
8. Which constraints belong in the database rather than only in Java?
9. What happens if two requests create the same watch simultaneously?
10. Which HTTP status should represent validation, missing resources and conflicts?
11. Where should business validation live?
12. Why use Flyway instead of letting Hibernate modify the production schema?

These questions prepare the ground for later topics such as transactions, concurrency, Redis, RabbitMQ, Kafka and distributed systems.

# 16. Product Principle

> **Build the simplest system that satisfies the current requirements, then introduce the next technology when a real requirement creates a reason for it.**

For PriceWatch:

- PostgreSQL before Redis.
- Synchronous REST before RabbitMQ.
- RabbitMQ before Kafka.
- PostgreSQL search before Elasticsearch.
- Local Docker before cloud deployment.
- ECS before Kubernetes.

Each technology should solve a problem that already exists in the project.

# Month 1 Final Outcome

At the end of Month 1, PriceWatch should be a small but properly structured backend—not a production-scale system.

A successful result is:

> **A tested Spring Boot REST API backed by PostgreSQL that allows users to create products, create price watches, and maintain price history through a clean API and database model.**

Everything more sophisticated comes later.
